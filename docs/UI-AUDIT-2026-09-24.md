# Buttons Bebe Support Console — Production UI Audit

**Date:** 24 September 2026\
**Target:** https://support.buttonsbebe.com/console/\
**Verdict:** Fix the P1 issues before treating the embedded inbox as a dependable working interface.\
**Method:** Read-only production observation, screenshots, computed layout measurements, accessibility-tree inspection, network-log inspection, and supporting local-source review. No fixes applied.

The visual reference was the app’s existing console styling and local design conventions. An assembled design-system canvas was not available through this session’s tools. Visual judgment was performed in a single context, not an independent blind screenshot review. Source pointers link to current files and name their functions/selectors so they remain useful as fixes move lines. The observations describe the original audit revision; source links are not proof that every deployed implementation detail matches it.

## Production safety and scope

- Inspected Overview, the already-loaded Tickets inbox, Connections, Knowledge base (including one existing document), Notice Board, Notifications, and Settings.
- Tested desktop at **1340 × 756**, the inbox at **1440 × 1000**, and selected responsive screens at **390 × 844**. Dimensions in this report are CSS pixels, not scaled screenshot pixels.
- Did **not** type into editors/composers or invoke save, send, rewrite, post-note, publish, delete, link/unlink, test-alert, notification-row, or mark-all-read actions.
- No production mutation endpoint appeared in the inspected network log during the audit. Inbox requests using `POST /inbox/console/api/helpdesk` are the app’s read RPC transport; the inspected production server allowlists read/status tools. This statement does not claim that normal request handling creates no infrastructure logs or caches.
- **Browser-local caveat:** the inbox became loaded during the session. Its source automatically selects the first ticket and persists read state to `localStorage` (`bb-inbox-read-v1`). That is not a Gorgias/server ticket write, but the session cannot be described as having zero browser-local state changes. Once identified, no further ticket selection or inbox preference changes were performed. The cause of the initial console tab transition was not established.
- Opening Notifications itself reads the feed. Clicking a notification row would mark it read on the server; those rows were not clicked.
- Restored the desktop viewport and left the console on Overview.
- The only intentional local repository addition is this report. No application code was changed.

## UI-01 — Draft/composer squeezes the conversation out of view

**Priority:** P1\
**Location:** Console → Tickets → selected ticket, central column.\
**Elements:** `iframe#inbox-frame` → `.pane-thread`, `[data-slot="thread"]`, `.thread-scroll`, `[data-slot="composer"]`, `.composer`, `.draft-strip`.

### Observed

At **1340 × 756**, the central pane was approximately **625px** tall, but:

- `[data-slot="thread"]` had only **22px** of height.
- `.thread-scroll` was only **28px** high.
- The composer occupied approximately **602px**.
- The composer started around **y=31px** within the iframe, overlapping the space used by the thread heading and controls.

The screenshot shows a large sensitive-draft block and reply editor, while the conversation and ticket heading are effectively obscured. Increasing the viewport to **1440 × 1000** did not resolve the problem: the conversation still measured only **27px** high.

### Why it matters

An agent cannot meaningfully inspect the customer conversation before assessing or sending the draft. More viewport height alone does not fix this case.

### Recommended fix

Constrain the draft/composer region and let its long content scroll or expand deliberately. Reserve usable space for the thread heading and conversation. Ensure the thread and composer remain non-overlapping siblings when either contains long content.

### Implementation pointers

- [Thread/composer slots: `.pane-thread > [data-slot]`](../console-src/inbox/styles.css) — thread can shrink; composer is nonshrinking.
- [Nested pane sizing: `.pane-inner`](../console-src/inbox/styles.css).
- [Conversation scroll area: `.thread-scroll`](../console-src/inbox/styles.css).
- [Composer sizing: `.composer`](../console-src/inbox/styles.css).
- [Draft sizing: `.draft-strip`](../console-src/inbox/styles.css).
- [Mobile draft cap: `.pane-thread .draft-strip`](../console-src/inbox/styles.css).
- [Thread/composer markup: `data-slot="thread"` / `data-slot="composer"`](../console-src/inbox/js/inbox.js).

**Acceptance:** With the same long draft, desktop at both tested sizes shows a readable conversation, visible ticket controls, and an accessible reply editor without overlap. Add a regression case with a long sensitive draft.

## UI-02 — Mobile ticket list collapses to zero height

**Priority:** P1\
**Location:** Console → Tickets at **390 × 844**.\
**Elements:** iframe → `.pane-list`, `.pane-list > .pane-inner`, `.list-toolbar`, `.history-notice`, `.ticket-list`, `.list-pagination`.

### Observed

The list panel measured **238px** internally, while `.ticket-list` measured **0px**. The screen showed search, Inbox controls, a long observed-history notice, and “Showing 100 of 3353 tickets,” but **no ticket rows**. The Load more control was also clipped at the panel boundary.

### Why it matters

The user cannot browse the list even though the count says that tickets are loaded. This is a layout failure, not an empty dataset.

### Recommended fix

Remove or revise the fixed mobile list-height budget. Reserve space for visible rows and place the verbose history explanation behind a concise summary/details disclosure, or use a dedicated mobile list/detail view. Keep pagination reachable.

- [Pagination sizing: `.list-pagination`](../console-src/inbox/styles.css).
- [List section ordering: `class="ticket-list"`](../console-src/inbox/js/tissues/list.js).

**Acceptance:** At 390 × 844, multiple ticket rows are visible without first dismissing informational content; list scrolling and pagination work. Also check a narrower 375px viewport in staging.

## UI-03 — Dashboard links do not preserve the metric/risk they advertise

**Priority:** P1\
**Location:** Overview → KPI cards, Needs your attention, Risk breakdown.\
**Elements:** `button.kpi[data-go-filter]`, `.attention-btn[data-go-filter]`, `.risk-link[data-go-filter]`.

### Evidence and limitation

The live DOM advertises distinct filters such as `draft`, `escalated`, `failed`, and `queue`. Risk controls similarly advertise `risk:critical`, `risk:high`, and other categories. In the checked-out source, `inboxDeepFilter()` maps those categories to **`all`** rather than an equivalent filtered inbox.

This was **not click-tested in production**, because mounting/selecting inbox tickets can change browser-local read state. Treat the deployed behavior as needing confirmation in staging, not as a completed production interaction test.

### Why it matters

A user selecting “Failed jobs,” “Recent escalations,” or “Critical” reasonably expects the matching items, not an unfiltered inbox. The wrong destination makes the dashboard an unreliable triage tool.

### Recommended fix

Carry supported predicates into the inbox URL/view state. If the destination cannot represent the metric, make the card informational or explicitly label a generic “Open inbox” action instead of implying a filtered drill-down.

### Implementation pointers

- [Filter normalization: `inboxDeepFilter()`](../console-src/index.html).
- [Inbox navigation: `goTickets()`](../console-src/index.html).
- [Metric and risk controls: `overview()`](../console-src/index.html).
- [Click binding: `bind()`](../console-src/index.html).

**Acceptance:** Every clickable metric opens the corresponding set or clearly communicates that no filtered drill-down is available. Test count scope separately: historical result totals and current ticket counts are not interchangeable.

## UI-04 — Connections uses success styling for unhealthy states

**Priority:** P1\
**Location:** Console → Connections.\
**Navigation selector:** `.nav a[data-tab="conns"]`.\
**Elements:** `.conns .conn .stt`, `.conns .conn .stt .dot.off`, `.panel .act .r .ic.g`.

### Observed

The following labels appeared inside green success-style badges:

- Shopify: **Needs refresh**.
- WhatsApp alerts: **Needs linking**.
- Knowledge base: **Content stale**.

The Health row said **“Knowledge-base content files need attention”** and **“refresh overdue”**, yet displayed a green check icon. The child status dot changes, but the badge itself retains success styling.

### Why it matters

A fast visual scan reads the screen as healthy while its text says intervention is required. The check icon specifically contradicts the message.

### Recommended fix

Apply state-specific badge and icon treatments: success for configured/healthy, warning for stale/refresh-needed, and a neutral or warning disconnected state for needs-linking. Preserve explicit text so the distinction does not depend on color alone.

### Implementation pointers

- [Connection badge styling: `.conn .stt`](../console-src/index.html).
- [Connection state rendering: `conns()`](../console-src/index.html).
- [Health icon selection: `conns()`](../console-src/index.html).

**Acceptance:** None of the three observed degraded states looks like a success state; a needs-attention health row no longer shows a success check.

## UI-05 — “Ready for review” mislabels an all-time draft total

**Priority:** P2\
**Location:** Overview → AI drafts written.\
**Element:** `button.kpi[aria-label="View AI drafts written tickets"]`, especially `.s`.

### Observed

The card showed **5,398** with supporting text **“ready for review.”** The source calculates this from cumulative result statuses (`drafted + sensitive_draft + no_kb_match`), not from unsent/unreviewed current tickets. The backend aggregation has no pending-review or latest-ticket filter.

### Why it matters

The label presents an output-history metric as actionable backlog. Operators may infer thousands of drafts await review when that has not been measured.

### Recommended fix

Label the current metric “created all-time” or equivalent. If a pending-review card is wanted, calculate a separate backlog count using the appropriate current-ticket and review/send state.

### Implementation pointers

- [Draft total and card caption: `overview()`](../console-src/index.html).
- [Cumulative backend aggregation: `get_result_stats()`](../webhook/src/bb_webhook/database.py).

**Acceptance:** The card’s time scope and workflow meaning match its query. Do not use “ready for review” unless the count actually represents currently reviewable work.

## UI-06 — WhatsApp setup is buried beneath the entire notification backlog

**Priority:** P2\
**Location:** Console → Notifications.\
**Navigation selector:** `.nav a[data-tab="notif"]`.\
**Elements:** `section[aria-labelledby="notification-title"]`, `.notification-list`, the following `.sec-title` and `.grid2b`, `#wa-save`.

### Observed

The page subtitle promises **“Link WhatsApp and choose where alerts go.”** However, all **86** notification rows render ahead of setup:

- The WhatsApp alerts heading was at approximately **y=8653px** from the initial page viewport.
- The content scroller had approximately **8978px** of content and **643px** of visible height.
- Setup required roughly thirteen screenfuls of scrolling, despite Connections explicitly directing the user there to scan the QR.

### Recommended fix

Separate “Activity” and “Alert delivery” into clear sections/tabs, put setup/status near the top, or add an obvious “Configure WhatsApp” jump link. Paginate or constrain the feed so its size does not determine setup discoverability.

### Implementation pointers

- [Notification list styling: `.notification-list`](../console-src/index.html).
- [WhatsApp setup markup: `notificationDelivery()`](../console-src/index.html).
- [Activity/delivery ordering: `notificationsView()`](../console-src/index.html).

**Acceptance:** A user arriving from Connections can find WhatsApp configuration within the first screen or via one clearly labeled navigation action, regardless of backlog size. Do not require marking notifications read to access setup.

## UI-07 — Console chrome and embedded inbox look like different products

**Priority:** P2\
**Location:** Console shell versus Tickets iframe.\
**Elements:** parent `body`, `.top`, `.nav`, versus iframe `body`, `.ticket-row`, `.thread-head`, `.composer`, `.btn-ink`.

### Observed

The console uses **Jost**, a sand sidebar, burgundy navigation/accent, and softer card/control shapes. Computed styles in the inbox use **IBM Plex Sans** (and mono treatments), rust accents, smaller corner radii, and dark primary controls. These differences are visible simultaneously on the Tickets screen.

This is a consistency finding, not a claim that either individual font or palette is inherently wrong.

### Recommended fix

Apply a small shared brand-token layer to the iframe: typography, accent, semantic colors, border colors, radii, and button treatments. Preserve the inbox’s useful information density rather than forcing dashboard-card spacing into a workbench.

### Implementation pointers

- [Console brand system](../console-src/brand/brand.css).
- [Console inlined brand override: `#buttonsbebe-brand`](../console-src/index.html).
- [Inbox theme and fonts: `#support-theme` / `#buttonsbebe-brand`](../console-src/inbox/index.html).
- [Older support-theme tokens](../console-src/support-theme.css).

**Acceptance:** Side-by-side screenshots look like one application, with deliberate workbench density differences rather than unrelated fonts and action colors.

## UI-08 — Owner-alert banner demands action without an actionable destination

**Priority:** P2\
**Location:** Overview → red owner-alert warning.\
**Element:** `.owner-alert-warning[role="alert"]`.

### Observed

The warning said **“710 owner alerts need review”** and instructed the user to **“inspect the affected ticket.”** It contained **no link or button**, no affected-ticket identifier, and no explanation of how this count relates to **86** unread notifications or **86** recent escalations.

The counts may refer to different populations; their difference alone is not evidence of a counting bug. The confirmed problem is missing scope/context and a route to the requested action.

### Recommended fix

Add a read-only drill-down for affected owner-alert records/tickets and label the count’s scope (for example, unresolved delivery attempts versus distinct tickets). If such a destination does not exist, say exactly where the operator can investigate instead of implying an available drill-down.

**Acceptance:** The user can identify the affected items from the banner without guessing which other count or screen to use. Visiting the inspection destination must not acknowledge or resend alerts automatically.

## UI-09 — Knowledge-base editor lacks an accessible name

### Observed

The textarea has no associated label, `aria-label`, or `aria-labelledby`. A nearby filename is displayed in a plain bold element, not connected to the field.

### Recommended fix

Associate the visible document heading with the textarea using a proper label or `aria-labelledby`. Give the editor a meaningful accessible name that includes its purpose and/or the current document.

### Implementation pointer

## UI-10 — Knowledge-base navigation hides the useful part of document titles

**Priority:** P2\
**Location:** Console → Knowledge base → left document list.\
**Elements:** `.kblist`, `.kbitem[data-open]`.

### Observed

At desktop width, the narrow list repeatedly shows generic prefixes such as **“Intent 1 — First-time customer asks f…”** and **“Intent 2 — Customer selected picku…”**. The more useful distinguishing clause is frequently truncated. Long titles also truncate at mobile width.

The native title tooltip contains the file path, not necessarily the full friendly title. Mobile users cannot rely on hover to reveal it.

### Recommended fix

Allow two-line titles, shorten repeated prefixes, or provide an accessible full-title reveal. Consider a simple filter for the 51-file list. Keep filenames available as secondary information rather than as the sole tooltip replacement for the hidden title.

### Implementation pointers

- [Document-title styling: `.kbitem`](../console-src/index.html).
- [Document-title/path rendering: `kbView()`](../console-src/index.html).

**Acceptance:** Users can distinguish similarly prefixed intents without opening each one, on desktop and touch screens. Full titles remain available to assistive technology.

## Lower-priority polish and follow-up checks

These are not blockers and should not distract from UI-01/UI-02.

1. **Overview KPI balance:** At 1340px the six KPI cards form a **5 + 1** layout, with In queue alone on a second row. Consider a 3 × 2 grid at that width or a six-column layout only when all six fit comfortably. Element: `.kpis`.
2. **Settings promises configuration but shows a passive checklist:** “Configure your agent” leads to setup rows without direct actions or explicit completed/remaining states. Either label this screen as setup/safety information or provide read-only navigation to the relevant screens. Do not add state-changing setup controls casually.
3. **Freshness language deserves review:** The header showed “Agent live” and a recent dashboard refresh, while recent activity was nine days old and product content was thirteen days old. These can legitimately measure different things. Label process health, last successful data refresh, and latest observed ticket separately; do not claim the system is broken from these timestamps alone.

## Checks that did not become findings

- The console’s only captured error was an authentication-session **401 before login**. It was not reported as a post-login application defect.
- The sampled console pages and inbox read requests returned successful responses after login; no failing post-login API response was confirmed.
- Brief blank/skeleton frames and transitional mobile sidebar positions were not treated as persistent rendering failures.
- Overview and the sampled Knowledge-base page did not show page-level horizontal overflow at 390px. The inbox’s vertical collapse is a separate confirmed defect.
- No write flows, production sends, refunds, notification acknowledgements, publishing, or editing were tested. No claim is made that those workflows pass.
- No assessment of ticket-data correctness, AI response correctness, or provider delivery success was performed.

## Suggested fix order

1. Repair the desktop conversation/composer height allocation and mobile ticket-list height; test long content first.
2. Correct dashboard drill-down semantics and misleading connection-health presentation.
3. Fix metric wording and the owner-alert investigation path.
4. Make alert-delivery setup immediately discoverable.
5. Address editor accessibility, document-title visibility, and shared brand styling.

**Design-system assessment:** The existing console has a recognizable brand treatment; the embedded inbox visibly diverges. No design-system delta was introduced by this audit because no application changes were made. Prefer aligning existing tokens and fixing sizing constraints over a broad redesign.
