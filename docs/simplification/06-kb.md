## Reliability risks

1. **Learning lock is a hard `fcntl.flock` with no stale handling, but `learned/` write concurrency is handled by a *different* mechanism per file.** `webhook/src/bb_webhook/learning.py:84-87` locks `_ledger.json.lock` with a blocking exclusive flock; lesson files themselves are published by `os.link` no-replace atomicity (`learning.py:63`). `auto_promote_learned` takes **no lock at all** over `learned/` — it relies on per-file atomic idempotency (`_write_idempotent`, `auto_promote_learned.py:59-87`, `os.link` + content-compare) and archive-move retry-safety (`:90-97,145-153`, all-or-nothing pair with rollback). Verified correct by tests: `test_auto_promote_learned.py:110-137` (archive failure rolls back exemplar; retry idempotent), `:56-97` (mask + dedupe), `:139-148` (legacy/unapproved never promote), `:150-157` (hash-bound content). Scenario: nightly promote runs at 03:30 UTC *while* a console action writes a lesson (owner works late). Consequence: none — `promote_one` either sees a complete file (front-matter parse fails → counted as failure, retried next night) or an identical pre-existing exemplar. The design is lock-free-correct by file atomicity. **No fix needed; this is the honest answer to "would a lock table be more correct": no.**
2. **Index vs corpus lock ordering — verified correct, no deadlock window.** Product sync takes sync lock → (stages corpus outside) → index lock (`write_files` `sync_products.py:568`) → commits corpus swap (`:569`) → rebuild inside `rebuild_index_locked` (`index_kb.py:137-172`), which itself takes only the promotion lock at swap time (`:77`). Readers take the shared promotion lock around `connect + both searches` (`search_kb.py:103-115`; lock-scope verified by `test_search_kb.py:193-214`). Manual `./update.sh` takes only the index lock (`index_kb.py:178-180`). Failure mid-rebuild: staging dir + backup are cleaned in `finally`/best-effort (`index_kb.py:96-97,170-172`); a crash between `os.replace(DB_DIR, backup)` and `os.replace(staged, DB_DIR)` (`index_kb.py:82-84`) leaves `DB_DIR` missing and a `.lancedb-backup-*` dir behind — **search then fails hard** (`lancedb.connect`/`open_table` on a missing dir raises; no try/except in `search()` around connect). Consequence window: a crash in the microseconds-long swap leaves the KB tool down until a human re-runs `update.sh` (or restores the backup dir by hand). Probability: very low (two adjacent renames), impact: high (Hermes loses `search_kb` → every draft degrades). Minimal fix (P2, ~8 LOC): on startup or in `search()`, if `DB_DIR` is missing, scan for `.lancedb-backup-*` and `os.replace` it back (self-healing last-known-good), or at minimum fail with "index directory missing — run ./update.sh" instead of a raw LanceDB traceback. Crash-mid-rebuild of the *corpus* swap has the same shape but is covered: `_restore_previous_products` handles the failure path (`sync_products.py:505-514`) — for crashes, the next sync re-validates retention against whatever corpus survived; and index-vs-corpus consistency is restored by the next `write_files` because the rebuild reads whatever corpus is on disk.
3. **Stale-lock handling: fcntl locks vanish when the process dies (kernel-owned) — correct; the notices lock does not, and its 60s takeover is the one true stale-lock dance in the module** (`notices_lib.py:93-104`). The three fcntl lock files (`.index_kb.lock`, `.index_kb.promote.lock`, `.products-sync.lock`) need no stale handling — that's the platform feature working. The lock *files* persist as zero-byte artifacts (e.g. `kb/.index_kb.lock` exists in the repo working tree, dated Sep 16) — harmless, gitignored (`.gitignore:44-46`). Answer to question (a): **the current design is already minimal and more correct than a SQLite lock table would be** — the corpus-restore transaction is filesystem work (rename/replace of directories, `sync_products.py:489-514`, `index_kb.py:75-97`) that SQLite cannot transactionalize; readers are a different process (the MCP service) sharing only the filesystem; and the promotion lock is held for exactly two renames, so a lock table would add a crash-consistency problem (who cleans the DB row?) to solve a non-problem. The only genuinely hand-rolled stale-lock logic (notices) is hand-rolled because it must interoperate with Node (`server.js:170-182`) — file-mtime takeover is the boring cross-language answer.
4. **`search_kb` has no handling for "index not built yet"** — first-run on a fresh VPS before `setup.sh` finishes, or the risk-2 crash window, surfaces as an unhandled LanceDB exception inside the MCP tool. The MCP server is `Restart=on-failure` (`buttonsbebe-kb-mcp.service:14`) but the tool call itself would return an error to Hermes. Low frequency, medium impact (Hermes runs without KB grounding). Minimal fix: same self-heal/friendly-error as risk 2; ~5 LOC. (Hunch-labeled: the exact LanceDB failure mode on a missing dir is version-dependent; treat the fix as "catch + log + return [] or a clear error", never as "silently return results".)
5. **The legacy human review gate (`review_learned.py` + `feedback/review.py` + console `/dashboard/api/review/*` routes) operates on `ticket-*.md` packets that nothing writes anymore.** Live capture writes `lesson-*.md` with `schema_version: 2` (`learning.py:139-141`); `review_learned.py:70` and `feedback/review.py:78` glob `ticket-*.md`; only the retired `feedback/collector.py:41-42` writes those (`feedback/collector.py` is the superseded poller, RETIRED.md:20). Consequence: the console's review list is permanently empty — an operator may believe the human gate is active when the live path is the nightly auto-promotion (which *is* the deliberate design, AGENTS.md §11: "nightly PII-masked promotion"). This is not a correctness bug in the live path; it is a dead-user-interface liability (misleading tooling). Minimal fix: retire `review_learned.py` + the `/dashboard/api/review/*` routes + `feedback/review.py` together per the RETIRED.md pattern, OR document at the top of both files that they are the legacy v1 gate superseded by `auto_promote_learned.py` (per instructions: do not propose reviving the human gate; the nightly auto path is deliberate). P2 (decision + deletion beats docs).
6. **`auto_promote_learned.main()` returns exit code 1 on any per-file failure but `learn-nightly.sh` is `set -e`** (`learn-nightly.sh:1-7`): if any lesson fails to promote, the script exits **before running `index_kb.py`**, so successfully promoted exemplars sit unindexed until the next fully-clean night. Consequence: a single malformed lesson file stalls indexing of all new exemplars indefinitely (a poison-pill). Minimal fix (~1 LOC): in `learn-nightly.sh` run promote and index as separate steps tolerant of promote's partial failure — `./.venv/bin/python scripts/auto_promote_learned.py || true` followed by index — or better: promote returns 0 unless *zero* promoted-and-failed... simplest correct shape: index unconditionally after promote (the exemplars on disk are the truth; failed lessons retry next night by design, `auto_promote_learned.py:145-153`). P2. (Verified `main()` returns `1 if failures else 0` at `:170`.)
7. **Nightly-learn ordering vs product-sync timer collision** — both end in `index_kb.py`, which fail-fasts on lock contention (`index_kb.py:46-47`). Learn runs 03:30 UTC (`buttonsbebe-kb-learn.timer:4` `OnCalendar=*-*-* 03:30:00`); sync runs 1d-after-last-run (`buttonsbebe-kb-sync.timer:6-7`), so it drifts. If they collide, one exits non-zero; with `Persistent=true` both timers retry on boot. Consequence: a skipped night of exemplar indexing (risk 6 compounds) — but the corpus/indexes stay consistent (that's the lock doing its job). No fix required beyond risk 6's unconditional index.
8. **`sync_products.mint_token` has no retry and a 30s timeout** (`sync_products.py:95-102`); bulk poll bound is hard (`MAX_BULK_POLLS=180`, `:40`, tested `test_sync_products.py:180-189`). A transient 5xx at token mint kills the sync (fail-closed — correct posture: no partial corpus). Consequence: sync retries next timer tick. Acceptable; document-only.
9. **NOT a risk (checked):** FTS keyword search is LanceDB's built-in `create_fts_index`/`query_type="fts"` (`index_kb.py:159-165`, `search_kb.py:111-115`) — **not hand-rolled**; SQLite FTS5 would not "do" here because the vector half needs the same table anyway (answer to question f: keyword side is platform-provided; the only hand-rolled ranking is RRF blending ~20 LOC at `search_kb.py:118-138`, which is the deliberate hybrid policy — category weights, identifier anchors, diversification — all tested in `test_search_kb.py:83-218`). Embedding source: fastembed with pinned local model `paraphrase-multilingual-MiniLM-L12-v2`, 384-dim (`kb_lib.py:58-59`) — **longevity risk noted**: the model is pinned by name and downloaded on first run (`SEARCH-ENGINE.md:94`); it is a small standard sentence-transformers model, CPU-only, no API — a 10-year-boring choice, but a future fastembed release could drop the default source; the pinned `requirements.lock` with hashes (`setup.sh:11`) pins the loader, not the model weights. Mitigation exists implicitly (the corpus outlives; re-embedding would be needed for any model swap — `update.sh` is the one command). No action beyond a one-line note in SEARCH-ENGINE.md (P3).
10. **NOT a risk (checked):** `sensitivity.py` is a clean data-driven tag table (`SENSITIVE_TAGS` frozenset `:14-42`, normalizer `:45-46`) — answer to question (g): yes, data-driven, fail-closed on malformed metadata (`:77-111`, tested `test_sensitivity.py:93-99`), single taxonomy shared by index and search via `kb_lib.py:28`. No scattered patterns. PII regexes likewise live in one table (`feedback/pii.py:23-44`) — the two are different axes (content risk vs personal data) and correctly separate modules.

## Rejected on principle

- **SQLite lock table instead of fcntl files:** the promote/corpus transactions are rename-based filesystem work; the lock's lifetime is a process lifetime (kernel-released on crash); a DB lock adds crash-state cleanup to solve nothing. The current design is the boring one.
- **SQLite FTS5 replacing LanceDB's FTS:** the vector half needs the rows anyway; two stores to keep in sync is worse than one hybrid table. (And LanceDB FTS is already the platform feature in use — nothing is hand-rolled here.)
- **New dependency (graphql-core) to replace the hand-rolled lexer:** two identical ~90-line lexers exist, but the fix is sharing one copy, not adding a parser dependency to a hash-pinned, offline venv that deliberately has six deps (`requirements.txt`); also fails the ≥100-line single-implementation bar (it's ~150 duplicated, ~90 each — consolidation, not a new wheel).
- **Unifying `sync_products.load_creds` on `feedback.config.load_env`:** would couple the KB venv (six deps, hash-pinned) to the feedback package's env and its Gorgias fields; 25 duplicated lines across three deliberately-independent processes is cheaper than the coupling.
- **filelock / portalocker for the fcntl locks:** stdlib `fcntl` is already the platform feature and is what the module uses; swapping adds a dep for zero behavior change.
- **Reviving or hardening the human review gate for v2 lessons:** the nightly auto-promotion with front-matter approval binding (`learning_approved`, `operation_id`, SHA-256 content hashes) is the deliberate design per AGENTS.md §11; the gate's remaining surface is legacy-only.
- **Auto-indexing `learned/`:** immutable safety model — `learned/` is PII-gated holding pen; promotion through masking is the only path. Not on the table regardless of simplification value.
- **Adding `products/` to git or reworking its generator output:** VPS-only generated data, gitignored by design; the corpus outlives the code.
- **Deleting the `kb/` copies of the systemd units:** the pair is test-enforced (`deploy/tests/test_warehouse_safety_assets.py:210-228`); removing one side breaks the gate and the deploy manifest's expectations. Consolidation would need the deploy test rewritten first — churn without longevity gain.
- **Locking `learned/` during promotion:** the design is already crash-correct via `os.link` idempotency + archive-pair rollback (verified risk 1); adding a nightly lock would serialize the promoter against live console writes for no failure it prevents.
