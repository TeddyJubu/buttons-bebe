## Duplication map

Within module:

1. **429 retry block duplicated** — gorgias_client.py:209-218 (`_post_message`) and gorgias_client.py:269-282 (`send_public_reply` history GET): identical `for attempt in range(_MAX_429_RETRIES+1)` + `_retry_after` sleep. One `_request()` helper would own it.
2. **`_SOURCE_CONTEXT_SQL` executed twice through two different connection styles** — send_intents.py:72 (read-only URI connection inside `review_context`) and send_intents.py:131 (same SQL inside the write transaction in `reserve`). The SQL constant is shared (good), but the surrounding row→recipient→draft-hash→conflict mapping logic is restated: `review_context` send_intents.py:74-83 vs `reserve` send_intents.py:134-141 (recipient derive + `draft_changed_refresh_ticket` + `new_customer_message_refresh_ticket`). Shared home: one `_context_checks(source, *, expected_revision, expected_recipient)` in `send_intents.py` used by both. ~20 LOC.
3. **`_GClient` + `_record_lesson` resolution trio** — routers/console.py:163-164, 185-186, 191-192 each repeat `_app_value("_GClient", _GClient), _app_value("_record_lesson", _record_lesson)`. A tiny module-level `_deps()` helper or functools.partial at router setup removes the repetition. Cosmetic.
4. **Login/session username resolution repeated** — routers/auth.py:44-46 `_session_username`, used by three handlers that each re-wrap the 503 (`_checked_username` routers/auth.py:57-61): acceptable; but `auth_check` and `auth_page_check` share the `_forwarded_mutation + trusted_origin` tail (routers/auth.py:145-147 vs 163-165). ~6 LOC.
5. **In-package HTML vs deploy copies** — `webhook/src/bb_webhook/review_console.html` is byte-identical to `deploy/review_console.html` (verified `git show` diff = IDENTICAL). Neither is served: no router references either file (grep for `review_console|dashboard.html` across `webhook/src/bb_webhook/`+`deploy/` returns zero code hits; Caddy serves `/var/www/console` from `console-src/index.html`+`login.html` via deploy/cd/source_release.py:121-130 `web/<name>` keys only). `dashboard.html` (in-package, 518 LOC) differs from retired `dashboard/index.html` and is served by nothing; AGENTS.md:92 says the live console SPA is `console-src/index.html`. Both in-package HTML files are dead weight shipped in the wheel (pyproject packages the whole `bb_webhook` dir).

Cross-module:

6. **Draft-token neutralization duplicated** — `rewrite_runner.neutralize` (rewrite_runner.py:21-22: `re.sub(r'</?DRAFT[^>]*>', '[untrusted draft marker]')`) vs `processor/hermes_runner/prompt.py:11-25` `_MARKER_SUBSTITUTIONS`/`_neutralise_markers` (same intent, different replacement strings). ## Reliability risks

1. **Owner alert "notifications" are derived, not durable — by design, with one gap.** notifications.py:1-6 derives the feed from current ticket rows; read-state lives in `app_settings` (routers/notifications.py:34-42). Scenario: a failed ticket is acknowledged (`mark read`), then a NEW failure arrives on the same message_id → `id = f"failed:{message_id}"` (notifications.py:44) collides with the acknowledged id → the new failure arrives pre-marked **read** and the owner never sees a badge. Evidence: `read` is keyed on `notification_id` alone (routers/notifications.py:41, 87-88), and the id embeds only message_id, not the failure timestamp or job_id. Consequence: silently missed failed ticket. Minimal fix: include `job_id` (already on ticket rows per database.py schema) or `occurred_at` in the id: `f"failed:{message_id}:{job_id}"`. One-line change + one test.
2. **Gorgias double-send risk is correctly contained — with one residual scenario.** `_post_message` retries only HTTP 429 (gorgias_client.py:209-218), never on `httpx.RequestError`; `send_public_reply` never re-POSTs an ambiguous result (send_intents.py:1-6 docstring; `reserve` returns the existing intent on retry, send_intents.py:123-130, 144-152; test_action_intents.py:66-79 asserts `len(calls)==1` after a TimeoutError). Residual: POST accepted by Gorgias but the client connection dies before the 201 body is read → `on_created` never fires → intent stays `uncertain` with no `remote_message_id` → status endpoint cannot reconcile (console_actions.py:140-144 requires `remote_message_id`). This is documented as the intentional fail-closed limit (webhook/docs/HUMAN-ACTIONS.md:34-37: "cannot be made exactly-once by this service alone… Inspect the ticket in Gorgias"). No code fix proposed — it is a documented operational limit, and the guard preventing auto-resend is tested (test_action_intents.py:82-109). Do not "fix".
3. **Delivery poll is 4×0.5s ≈ 2s max (gorgias_client.py:42-43, 365-397)** — an email channel that takes >2s to flip `sent_datetime` returns `pending` (202) and the operator must hit the status endpoint. Not a bug (status GET reconciles, console_actions.py:140-155) but worth knowing: sends will frequently show "pending" in the UI. Minimal improvement if desired: reuse the existing `_retry_after`-style backoff (0.5→1→2s) — same 4 polls, ~4s window. Low priority.
4. **`session_store.authenticate` registers v1 tokens then checks a row whose `expires_at` it just wrote from claims** (session_store.py:34-46): for v2 tokens the registry row is authoritative (must exist); for v1 it self-registers — meaning a v1 token's "revocation" only works if logout saw it first (revoke also registers, session_store.py:49-53). Covered by tests (test_session_security.py:77-86: tombstones can't be reactivated). Risk is accepted; the v1 path is a bounded migration (bcrypt-era). After migration completes, v1 support (console_auth.py:131-133, session_store.py:35-36) can be deleted — ~15 LOC. Mark for retirement once the bcrypt hash is rotated.
5. **`learning.py` fsync/link choreography is heavier than the KB-side lock pattern but not wrong.** `_write_unique_lesson` (learning.py:53-77): mkstemp → fsync → `os.link` retry loop → dir fsync; `_bump_ledger` (learning.py:80-123): flock on `_ledger.json.lock` → read → temp write → fsync → `os.replace` → unlock. Compare KB side: `kb/scripts/sync_products.py:47-57` and `index_kb.py:40-46` use plain `fcntl.flock(LOCK_EX | LOCK_NB)` with fail-fast. Differences: (a) learning takes a *blocking* lock — a hung holder stalls a console send response (capture_learning runs inline in the send path, console_actions.py:127) but it's guarded: `capture_learning` swallows exceptions and logs (console_actions.py:36-38), so a stuck lock degrades to "lesson not captured, retryable via action status", not a failed send; (b) the ledger keeps an unbounded `_operations` id list in the JSON (learning.py:93-98) — grows by one UUID per send forever. At ~2k tickets/month this is ~24k UUIDs/year (~800 KB/yr) read+rewritten fully under the lock on every action. Simplest correct version: move dedupe to the `learning_recorded` column it already maintains (send_intents.py:199-201 marks the intent row; `capture_learning` checks `row['learning_recorded']` first, console_actions.py:27) and drop `_operations` from the ledger — the SQLite flag is the real dedupe; the JSON list is a second, weaker copy. ~10 LOC out, one less unbounded structure. (The kb tests test the JSON-list path specifically — kb/tests/test_auto_promote_learned.py:99-104 — and would need updating.)
6. **`result_auth.authorized` compares the whole header string constant-time** (result_auth.py:12) — fine, but it means `Bearer <secret> extra` fails (good) and a missing header becomes `""` (handled). No risk. The two-auth-systems question (g): session auth authenticates the *human owner* via cookie; result auth authenticates the *processor process* via loopback + Bearer secret (middleware/console_session.py:41-51). They are different principals (owner:chaim vs processor), different transport (cookie vs header), different network position (public-via-Caddy vs loopback-only). Overlap is only the `hmac.compare_digest` habit — correctly used in both (console_auth.py:79, result_auth.py:12). Two systems are justified; do not merge.
7. **`password_executor` process pool**: capacity 2 with non-blocking semaphore (password_executor.py:11-12, 41-42); saturation returns 429 without blocking intake (tested test_session_security.py:154-170). One subtlety: the pool is created lazily on first use with `spawn` (password_executor.py:28) — on a forked-then-threaded server the spawn cost (~100-300 ms) lands on the first login after boot; acceptable. `BrokenProcessPool` handling discards and recreates (password_executor.py:32-37, 46-49). No fix needed.
8. **`review_context` opens its own read-only aiosqlite connection with `mode=ro` URI and 0.2s timeout** (send_intents.py:67-71) while every other DB access goes through `Database` (db.py) with 3s busy_timeout + retry. Scenario: brief write-lock contention during a console burst → `review_context` raises `aiosqlite.OperationalError` after 0.2s → route returns 503 `review_context_unavailable` (routers/console.py:138-140) instead of retrying like everything else. Consequence: transient, self-healing UI hiccup on the dormant inbox path. Minimal fix: reuse `self.db.fetch` for the read (it's `PRAGMA query_only`-equivalent since it only SELECTs) and let db.py's retry handle contention — removes the bespoke connection ~10 LOC. Low priority (dormant route).

## Rejected on principle

- Switching the HMAC session token to `itsdangerous`/JWT: breaks the sha256-canonical-token registry and revocation tombstones for zero functional gain.
- Adding `passlib`/`bcrypt` as a dependency: `hashlib.pbkdf2_hmac` is stdlib and already correct; bcrypt support exists only as a bounded migration path.
- Generic HTTP transport-level retries on the Gorgias POST: would violate the no-auto-resend invariant that the intent store exists to enforce.
- Merging session auth and processor result auth: different principals (owner vs processor), transports, and network positions — the split is the security model (middleware/console_session.py:41-51).
- Making learning capture blocking-strict or alerting on failure: it's deliberately non-fatal to the send (console_actions.py:36-38); the action row retains retry state.
- "Fixing" the ambiguous-POST edge (accepted-but-connection-died) with an auto-reconcile or resend API: explicitly forbidden by webhook/docs/HUMAN-ACTIONS.md:34-37; fail-closed is the requirement.
- Serving the in-package HTML from the FastAPI app to "make them live": they are superseded snapshots; reviving them creates a second console.
- Replacing `password_executor` with a thread pool: comment explains spawn isolates crypt GIL stalls (password_executor.py:26-28) — the complexity is load-bearing.
- Idempotency-key header API at the Gorgias client layer: Gorgias has no documented idempotency key; the intent store already provides the equivalent at the right layer.
